# Commit Message Discipline

A commit message is a contract with the future archaeologist who reads it without your context. Vague messages ("fix", "update", "wip") tell them nothing; over-claimed messages ("refactor" for a one-line typo) erode trust in the log. This skill drafts the message from the **actual staged diff**, verifies it against the change, and refuses to ship a message that misrepresents the bytes.

## When to load

Load this skill when:
- The staging area is set (`git diff --cached` shows the intended change).
- You have already inspected the diff (not just `git add -A` on a guess).
- You are about to run `git commit` and the message matters — public history, shared branch, or a PR that will be reviewed.

Do **not** load this skill for:
- Trivial local WIP snapshots where the message will be rewritten before push.
- Merge commits generated by git itself (those use the default merge message).
- Amending a published commit — that needs explicit user approval, not a message draft.

## Preconditions

1. **Staged diff is final.** Run `git diff --cached` and read every hunk. If anything staged is not yours to commit, unstage it. This skill does not run `git add` — staging is the user's approval boundary.
2. **No untracked files you intend to include.** Untracked files are invisible to `git diff --cached`; add them first, then re-inspect.
3. **Working tree is otherwise quiet.** Concurrent writers (another agent, an editor's auto-save) can change the staged set under you. Run `git status --short` and confirm the staged column matches what you inspected.
4. **You know the project's commit convention.** Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `perf:`, `test:`, `ci:`, `build:`, `style:`) is the default. If the project's `CONTRIBUTING.md` or recent `git log --oneline -20` shows a different convention, follow that instead.

## The procedure

### 1. Read the staged diff as a whole

```bash
git diff --cached
git diff --cached --stat
```

Ask one question of the entire change, not file-by-file: **what is the user-facing effect of this commit?** A four-file change that together adds input validation is one commit (`fix: validate input before processing`). The same four files touched for unrelated reasons is two commits, not one — split before drafting.

### 2. Infer the type from the effect, not the file path

| Effect on the project | Type |
|---|---|
| New feature, new capability, new user-facing behavior | `feat` |
| Bug fix — behavior restored to spec | `fix` |
| Documentation only (`.md`, comments that ship in docs) | `docs` |
| Code structure change with no behavior change | `refactor` |
| Performance improvement, measured or self-evident | `perf` |
| Test additions or corrections | `test` |
| CI/build/pipeline config | `ci` / `build` |
| Tooling, deps, scripts, housekeeping with no user-facing effect | `chore` |
| Whitespace, formatting, import order — no logic | `style` |

If two types apply equally (e.g. a fix that also refactors), pick the **higher-stakes** one — `fix` over `refactor`, because a reviewer reading the log should see the user-impactful framing first. Mention the secondary in the body.

### 3. Identify the scope (optional, when the project uses scopes)

The scope is the part of the codebase this change lives in — a module name, a package, a component. Infer it from the **most-touched directory**, not from a guess. Three files under `skills/computer-use/` → scope is `computer-use`. A change touching five unrelated top-level dirs → **omit the scope**, not invent one.

### 4. Draft the subject (one line, imperative mood, ≤72 chars)

The subject is a command, not a description:

- ✅ `fix(api): reject empty Authorization header before decoding`
- ❌ `fixed empty auth header bug` (past tense, vague)
- ❌ `update` (no verb, no object)

Cap at 72 characters. Git tools truncate at 50 for tight layouts; the rest is body territory. Do **not** end the subject with a period.

### 5. Draft the body (optional, when the subject alone is insufficient)

Leave one blank line after the subject. The body answers **why** this change exists, not **what** it does — the diff already shows what. Wrap at 72 characters.

- The bug it fixes, with a one-line reproduction if non-obvious.
- The constraint that forced this approach over the obvious alternative.
- A breaking-change footer if applicable (`BREAKING CHANGE: <description>` on its own line).
- Issue references (`Closes #123`, `Refs #456`) on their own lines, separated by a blank line from the rest of the body.

### 6. Flag breaking changes explicitly

A breaking change is one that requires consumers to change their own code. Use the footer, not the subject:

```
feat(api)!: rename `authToken` to `accessToken`

The old name suggested session-only use; the new name covers API keys
and service tokens too. Consumers must update their config.

BREAKING CHANGE: `authToken` renamed to `accessToken`. Config files
and environment variables referencing the old name must be updated.
```

The `!` after the scope is the subject-level flag; the `BREAKING CHANGE:` footer is the machine-readable one. Use both — some tools only read the footer.

### 7. Verify the draft against the diff (do not skip)

Before writing the commit, re-read your draft and ask:

- [ ] Does the **type** match the dominant effect? (Not just the largest file.)
- [ ] Does the **scope** (if any) name the actual module touched?
- [ ] Does the **subject** describe what a reviewer will see in the diff, in imperative mood, ≤72 chars?
- [ ] Does the **body** explain *why*, not *what*?
- [ ] Is every `BREAKING CHANGE:` claim actually breaking — not just inconvenient?
- [ ] Are issue references real and open (or being closed by this commit)?
- [ ] No invented context — no fake ticket numbers, no fabricated reviewers, no claims the diff does not support.

If any box fails, rewrite the draft. Do not commit a message that misrepresents the diff.

### 8. Write the commit

```bash
git commit -F .git/COMMIT_EDITMSG.draft
# or, for a single-line message:
git commit -m "fix(api): reject empty Authorization header before decoding"
```

Prefer the `-F` form for any message with a body — it preserves newlines and avoids shell-quoting accidents. Delete the draft file after the commit.

## Failure modes

- **Mixed-concern staging.** The diff touches validation AND a unrelated formatting change. Refuse to draft — ask the user to split the commit. Drafting a message for a mixed commit produces a message that is true for neither concern.
- **Empty staged diff.** `git diff --cached` shows nothing. Refuse to commit — there is nothing to describe. Check whether `git add` was run, or whether the changes are in the working tree only.
- **Type drift.** The diff renames a variable across 40 files — that is `refactor`, not `fix`, even if the rename was triggered by a bug. The trigger is the user's problem; the commit's effect is what the log records.
- **Scope invented.** No single module dominates the diff. Omit the scope; do not pick one to look tidy.
- **Breaking change over-claim.** An internal rename that no consumer sees is not breaking. Reserve the `!` and the `BREAKING CHANGE:` footer for changes that actually break callers.
- **AI-assisted authorship.** If the commit was prepared with AI assistance and the project requires disclosure, include it accurately in the body or a `Generated-with:` trailer. Do **not** claim a human review that did not happen, or a passing test that was not run. Authorship of the commit and authorship of the reasoning are separate concerns.

## Completion evidence

The commit is not "done" until you can show:

```bash
git log -1 --format='%an <%ae>%n%n%s%n%n%b'
git show --stat HEAD
```

- The log shows the author, subject, and body you intended.
- `git show --stat` confirms the files changed match what you staged.
- The message describes the diff, not a hope about the diff.

If the project runs pre-commit hooks (`pre-commit`, husky, a `core.hooksPath`), confirm they passed — a hook that rewrote your message means your draft is not what shipped. Read the actual message from `git log`, not from your draft file.

## Approval boundaries

- **Never amend a published commit.** If a commit has been pushed to a shared branch, amending it rewrites history others may have built on. Ship a follow-up `fix:` commit instead. Amending requires explicit user approval, in writing, per shared branch.
- **Never force-push to a shared branch without the user's explicit OK.** This skill does not authorize force pushes; it only drafts messages.
- **Never fabricate co-authors or reviewers.** `Co-authored-by:` trailers must name real people who actually contributed. A co-author trailer for an AI tool is fine if the project allows it; a co-author trailer for a human who did not contribute is fraud.
- **Never commit secrets.** If the staged diff contains a token, key, or credential, refuse to draft and abort. Unstage, scrub the secret, rotate it, then re-stage. A commit message cannot un-ring that bell.

## When to split before drafting

Drafting fails on mixed concerns. Split when:

- The diff touches two unrelated modules with no shared effect.
- One file adds a feature and another fixes an unrelated bug.
- A refactor and a behavior change share a file but not a reason.
- Tests for the change are in the same diff but the change itself is large enough that the tests deserve their own commit (project convention dependent).

After splitting, draft each commit independently — re-read its own staged diff, infer its own type, write its own subject. Do not reuse a draft across commits.
